1. Panoramica Sistema

Il sistema di Risk Management di VinciTu gestisce l'intero ciclo di vita di una scommessa dal punto di vista del rischio e della liability. Ogni bet passa attraverso validazione, analisi rischio, controllo liability e sistema di accettazione prima di essere confermata.

Componenti principali

ComponenteDescrizioneFile
Bet Placement APIPiazzamento server-side sicuro/api/player/place-bet
Risk Engine12 regole + 4 batch + AI Claudelib/risk/engine.ts
Liability EngineEsposizione per outcome/market/eventolib/risk/engine.ts
Acceptance EngineAuto/manuale/parzialelib/risk/engine.ts
Trading QueueCoda bet per review admin/api/admin/trading-queue
AI Odds OptimizerClaude suggerisce aggiustamenti quotelib/risk/engine.ts
Admin Panel6 tab: dashboard, alert, queue, liability, utenti, AI/admin/risk
NotificheRealtime + browser push per alert criticiadmin_notifications
Cron ScannerBatch pattern detection orario/api/cron/risk-scan
Architettura: Tutte le operazioni di scrittura avvengono server-side tramite API routes. Il frontend non ha accesso diretto in scrittura a Supabase per le bet. Questo previene manipolazioni client-side.

2. Piazzamento Scommesse

Endpoint: POST /api/player/place-bet

Flusso completo

Auth (cookie) → User check → Limiti utente → Validazione quote → Liability check → Acceptance engine → Insert bet → Risk analysis → Wallet deduction → Response

Request body

{
  "stake": 50,
  "selections": [
    { "eventId": "uuid", "marketId": "uuid", "outcomeId": "uuid", "odds": 2.9 }
  ],
  "fingerprint": "optional-device-id"
}

ACCOUNT_BLOCKEDAccount sospeso/bannatoMostrare errore

DAILY_LIMIT_EXCEEDEDLimite giornaliero raggiuntoMostrare residuo
ODDS_CHANGEDQuote cambiate oltre tolleranza (±0.05)Aggiornare schedina con nuove quote

Optimistic Concurrency: Il wallet viene detratto con WHERE balance = expected_value. Se il saldo cambia tra il check e la deduzione (race condition), il sistema riprova una volta con il saldo aggiornato.

4. Analisi AI (Claude)

Quando il risk score supera la soglia (default: 60), viene attivata l'analisi AI tramite Claude per una valutazione avanzata.

Input all'AI

  • Dati bet corrente: stake, quote, tipo, vincita potenziale
  • Profilo utente: KYC, classe, paese, età account
  • Player profile: classificazione, totali, win rate, GGR
  • Storico ultime 50 scommesse
  • Flags del rule engine

Output AI

{
  "score": 0-100,
  "level": "low" | "medium" | "high" | "critical",
  "flags": ["detected issues"],
  "player_classification": "recreational" | "semi_pro" | "sharp" | "syndicate",
  "confidence": 0.0-1.0,
  "recommended_actions": ["actions"],
  "reasoning": "spiegazione"
}

Il score finale è il massimo tra score regole e score AI. La classificazione AI aggiorna il player profile.

Modello: claude-sonnet-4-20250514 — configurabile in risk_config.ai_settings. Se l'API AI fallisce, la bet non viene bloccata (fail-open).

5. Liability Management

La liability (esposizione) rappresenta quanto il bookmaker rischia di pagare se un esito si verifica.

Formula

Liability per outcome = SUM(stake × (odds - 1))  per tutte le bet aperte su quell'esito

Limiti default

LivelloMax Liability
Per outcome$50,000
Per market$75,000
Per evento$100,000
Globale$500,000

SQL Functions

  • compute_outcome_liability(p_outcome_id) — calcola liability su un singolo esito
  • compute_event_liability(p_event_id) — calcola liability per tutti gli esiti di un evento

Soglie di allerta

% utilizzataAzione
> 70%Trigger rebalance (AI optimizer)
> 80%Alert admin
> 95%Sospensione automatica esito
100%Bet rifiutata o accettazione parziale

6. Sistema di Accettazione

Modalità

ModalitàDescrizione
AUTO (default)Tutte le bet accettate automaticamente, tranne se bloccate da liability o risk
MANUALTutte le bet vanno in trading queue per approvazione
HYBRIDBet sotto soglia → auto. Sopra soglia → manual review

Configurazione (risk_config.acceptance)

{
  "mode": "auto",
  "auto_accept_max_stake": 1000,
  "manual_review_stake_threshold": 5000,
  "partial_accept_enabled": true,
  "odds_change_tolerance": 0.05,
  "live_bet_delay_seconds": 5,
  "always_manual_classes": ["sharp", "syndicate"],
  "sharp_player_mode": "manual",
  "max_liability_per_outcome": 50000,
  "max_liability_per_market": 75000,
  "max_liability_per_event": 100000
}

Flusso decisionale

  1. Classe giocatore in always_manual_classes?
    • sharp_player_mode = "block" → RIFIUTATA
    • sharp_player_mode = "manual" → MANUAL REVIEW
  2. Stake > soglia manuale (in hybrid/manual)? → MANUAL REVIEW
  3. Liability superata?
    • Spazio rimasto > $1 + partial enabled → PARZIALE (stake ridotto al max consentito)
    • Spazio = 0 → RIFIUTATA
  4. Nessun problema → ACCETTATA

7. Trading Queue

Endpoint: /api/admin/trading-queue

Le bet con status pending_acceptance finiscono nella trading queue. Il wallet del giocatore non viene detratto fino all'approvazione.

API

MetodoDescrizione
GETLista bet pending con info utente, evento, quote, risk score
PATCHAccetta, rifiuta o accetta parzialmente una bet

Azioni admin

AzioneEffetto
AccettaStatus → open, wallet detratto, transazione creata
Accetta parzialeStake ridotto, wallet detratto per importo ridotto
RifiutaStatus → rejected, wallet invariato

Ogni azione viene registrata nella tabella risk_actions (audit trail) con il campo performed_by che identifica il trader.

8. AI Odds Optimizer

L'ottimizzatore AI analizza la liability per evento e suggerisce aggiustamenti alle quote per bilanciare il book.

Come funziona

  1. Raccoglie tutti i mercati + esiti + liability per un evento
  2. Calcola margine implicito e distribuzione esposizione
  3. Invia a Claude con regole: margine min 2.5%, aggiustamenti conservativi (0.05-0.20)
  4. Claude restituisce suggerimenti: outcome_id, current_odds, suggested_odds, reason
  5. Admin può applicare i suggerimenti (log in odds_adjustments)

Trigger

  • Manuale: bottone "AI Optimize" nella tab Liability dell'admin panel
  • Automatico: cron orario su eventi con liability > 70% del limite

12. Cron Jobs

Risk Scanner (ogni ora)

Endpoint: POST /api/cron/risk-scan
Auth: header x-cron-key = CRON_SECRET

  1. Trova utenti con ≥ 10 bet nelle ultime 24 ore
  2. Ricalcola player_profiles per ciascuno
  3. Esegue batch pattern detection (regole 13-16)
  4. Crea risk_flags per anomalie trovate
  5. Crea admin_notifications per alert critici
  6. Esegue AI odds optimizer su eventi ad alta liability

Daily Stats (ogni giorno alle 00:15)

Endpoint: POST /api/cron/daily-stats
Auth: header x-cron-key = CRON_SECRET

Aggrega per il giorno precedente: bet_count, total_stake, total_payout, GGR, margin_pct, deposit/withdrawal count+volume, active_users, new_users, risk_alerts, sport_breakdown. Upsert in daily_stats.

Setup VPS (crontab)

# Risk scan ogni ora
0 * * * * curl -s -X POST http://localhost:3000/api/cron/risk-scan -H "x-cron-key: $CRON_SECRET"

# Daily stats alle 00:15
15 0 * * * curl -s -X POST http://localhost:3000/api/cron/daily-stats -H "x-cron-key: $CRON_SECRET"

14. Configurazione

Tutta la configurazione è nella tabella risk_config con 6 chiavi JSON:

ChiaveContenuto
thresholdsSoglie auto-actions: auto_block (85), auto_flag (50), auto_reduce_limits (60), auto_kyc (40)
auto_actionsToggle: block_account, reduce_limits, require_kyc, notify_admin
rulesParametri regole: stake thresholds, odds limits, velocity limits, win rate
ai_settingsModello Claude, max_tokens, soglia attivazione AI
acceptanceModalità, soglie, partial accept, classi manuali
liabilityLimiti globali, soglie alert/suspend, AI optimizer settings

Modificabile dalla pagina /admin/config. Ogni chiave ha valori default hardcoded nel codice come fallback.
